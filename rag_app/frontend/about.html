📖 About this RAG App

Chat Admin

This app is a Retrieval-Augmented Generation (RAG) system. It doesn't just extract text — every question runs through a multi-stage pipeline of query enhancement, hybrid retrieval, and reranking before the LLM ever writes a word.

What is RAG?

Large language models are great at reasoning and writing, but they only know what was in their training data — nothing about your documents, and they can hallucinate when asked about things they don't know.

Retrieval-Augmented Generation fixes this by splitting the problem in two:

  • Retrieval — find the passages from your documents most relevant to the question.
  • Generation — hand those passages to the LLM as context and instruct it to answer strictly from them, citing its sources.

The result: answers grounded in your own documents, with citations, and a clear "I don't know" when the documents don't cover it.

The two pipelines

1 · Ingestion pipeline (when an admin uploads a document)

Load & parse→ Semantic chunking→ Embed→ Index (FAISS + BM25)
  • Load & parse — PDF (PyMuPDF), DOCX (docx2txt), TXT/MD loaders turn files into raw text with metadata.
  • Semantic chunking — instead of cutting text every N characters, an embedding model measures how similar adjacent sentences are and splits where the topic shifts. Chunks stay coherent, so retrieval returns complete thoughts, not fragments. Oversized chunks are re-split recursively as a safety net.
  • Embedding — each chunk is converted to a 384-dimension vector with all-MiniLM-L6-v2, running locally at zero API cost. Similar meanings land close together in vector space.
  • Dual indexing — vectors go into a FAISS index (persisted to disk) for semantic search, and the same chunks feed a BM25 keyword index for exact-term search.

2 · Query pipeline (when anyone asks a question)

Query enhancement→ Hybrid retrieval→ Rank fusion→ Reranking→ Grounded generation

Each stage below is a technique in its own right.

Techniques used

Query expansion query enhancement

Users rarely phrase questions the way documents phrase answers. Before searching, the LLM rewrites your question with synonyms and related terms — "How do I add memory?" also searches for "conversation history", "state persistence", and so on. Both the original and expanded queries are retrieved against, so nothing is lost if the rewrite misses.

HyDE — Hypothetical Document Embeddings query enhancement

A question and its answer often look nothing alike in vector space. HyDE bridges that gap: the LLM writes a short hypothetical answer to your question, and that imagined answer — which resembles real document passages far more than the question does — is embedded and used to search the vector store.

Hybrid search: dense + sparse retrieval

Two retrievers with complementary strengths run in parallel:

  • Dense (FAISS) — vector similarity finds passages that mean the same thing even with completely different wording.
  • Sparse (BM25) — classic keyword scoring nails exact terms, names, acronyms, and error codes that embeddings can blur.

MMR — Maximal Marginal Relevance retrieval

Plain similarity search can return five near-duplicate chunks from the same paragraph. The dense retriever instead uses MMR, which balances relevance against novelty: each result must be relevant to the query and different from the results already picked, so the context window covers more ground.

Reciprocal Rank Fusion fusion

Dense scores and BM25 scores live on incompatible scales, so they can't simply be added. RRF merges the ranked lists using only positions: each document earns weight / (60 + rank) from every list it appears in. Documents that multiple retrievers — and multiple query variants — agree on rise to the top.

Cross-encoder reranking reranking

Retrieval embeds the query and documents separately, which is fast but approximate. The fused candidates get a second, more careful pass: a cross-encoder (ms-marco-MiniLM-L-6-v2) reads the question and each chunk together and scores true relevance. Only the top few reranked chunks make it into the LLM's context.

Grounded generation with citations generation

The winning chunks — each labelled with its source document — are packed into the prompt, and the LLM (Groq-hosted llama-3.3-70b-versatile) is instructed to answer strictly from that context. Every answer reports which documents it drew from.

Why all this instead of simple text search?

Any single technique has a failure mode: pure vector search misses exact keywords, pure keyword search misses paraphrases, naive chunking splits ideas mid-sentence, and questions often don't resemble their answers. Layering these techniques means each one covers the others' blind spots — the LLM sees fewer, better chunks, and the answers are more accurate and better grounded.

Embeddings and reranking run locally (sentence-transformers); only query enhancement and the final answer use the LLM. The FAISS index persists to disk, so ingested documents survive restarts.
